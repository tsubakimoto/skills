# Search guidance

## Query construction

識別力が高い順に検索する。

| 優先度 | 検索要素 | 例 |
|---|---|---|
| 1 | エラーコード・完全なエラー文 | `site:azure.github.io/jpazpaas "Failed to fetch" "AI Search"` |
| 2 | サービス＋具体的な症状 | `site:azure.github.io/jpazpaas Azure App Service WebJob デプロイ 直後 実行` |
| 3 | 正式な設定名・機能名 | `site:azure.github.io/jpazpaas Azure Functions FUNCTIONS_WORKER_RUNTIME` |
| 4 | 上位概念・同義語 | `site:azure.github.io/jpazpaas BLOB 削除 RBAC ロール` |

検索結果が多すぎる場合は、OS、ランタイム、認証方式、ネットワーク構成を追加する。結果がない場合は、エラー文の引用符を外す、製品名を英語へ変える、症状を短くする、の順で広げる。

## Relevance checks

候補記事の本文を読み、次を確認する。

- 質問と同じサービス・機能か
- 同じ症状またはエラーか
- 同じOS、ホスティングモデル、ランタイム、SKUか
- 原因または制約が本文で説明されているか
- 対処が現在の質問へそのまま適用できるか
- 記事の公開・更新日や記載された基準日が古すぎないか

タイトルが似ていても、適用条件が違えば直接の根拠にしない。関連するが条件が違う記事は「参考情報」として区別する。

## Evidence handling

- 記事本文の要点を自分の言葉で要約する。
- 短い製品名、設定名、エラー文字列以外の長文引用は避ける。
- 複数記事が矛盾する場合は、更新時点と対象条件を比較し、解消できなければ両方を示して断定を避ける。
- 記事内の画面名や手順が現行ポータルと異なる可能性がある場合は、その旨を添える。

## Search failure

次の場合は「該当記事なし」と判断する。

- サイト限定検索で関連候補が出ない
- 候補の本文が質問と異なるサービスまたは条件を扱っている
- スニペットには語があるが本文に根拠がない

この場合、Microsoft Learn での追加調査を提案する。ユーザーが希望したら、Microsoft Learn を検索して別の根拠として回答する。
